# api_prime_pricing
Api pour prédire le prix de la prime en se basant sur la fréquence des accidents et la sévérité.

Consignes pour pousser des améliorations depuis ta branche de développement `dev_serge` vers `main`.

1) Préparer et committer mes changements sur `dev_serge`

```bash
# être sur la branche dev_serge
git checkout dev_serge

# vérifier l'état et ajouter toutes les modifications
git status
git add -A
git commit -m "Description courte de l'amélioration"
```

2) Pousser la branche distante (upstream)

```bash
git push origin dev_serge
```

3) Ouvrir une Pull Request (PR) sur GitHub (optionnel via CLI)

```bash
# crée une PR de dev_serge vers main
gh pr create --base main --head dev_serge --title "Titre de la PR" --body "Description détaillée"
```

Si une PR existe déjà, pousser mettra automatiquement à jour la PR ouverte.

4) Vérifier la PR (checks, revue, conflits)

```bash
gh pr view --web    # ouvre la PR dans le navigateur
gh pr checks <num>  # affiche le statut des checks
```

5) Fusionner la PR (après approbation et checks passés)

```bash
# merge (merge commit)
gh pr merge <num> --merge

# ou : squash
gh pr merge <num> --squash

# ou : rebase
gh pr merge <num> --rebase
```

6) Après fusion, mettre à jour ta branche locale `dev_serge` depuis `main` pour poursuivre le dev

```bash
# récupérer main
git checkout main
git pull origin main

# re-créer / synchroniser dev_serge depuis main (optionnel)
git checkout dev_serge
git merge main
# ou si tu veux rebaser
git rebase main
```

Remarques et bonnes pratiques
- N'ajoute pas de gros fichiers binaires dans le dépôt (utilise un stockage externe ou Git LFS si nécessaire).
- Garde `.code-workspace` dans `.gitignore` (déjà configuré dans ce projet), ne le commite pas.
- Pour éviter les pertes : fais des commits atomiques et pushes fréquents.
- En cas de conflit lors du merge/rebase, résous localement puis `git add` + `git rebase --continue` ou `git commit` selon la stratégie.

## Environment & installation

- Installer avec `pip` (virtualenv / venv - reproduction simple, best-effort):

```bash
# créer et activer un virtualenv
python -m venv .venv
source .venv/bin/activate

# installer les dépendances listées (fichier `requirements.txt` simplifié)
pip install -r requirements.txt
```

- Installer avec `conda` (recommandé si l'environnement d'origine est conda):

```bash
# exporter l'environnement source (sur la machine d'origine)
conda env export --name env_MATHS_FINANCE_DS_ML --no-builds > environment.yml

# créer l'env sur la machine cible
conda env create -f environment.yml
# activer
conda activate env_MATHS_FINANCE_DS_ML
```

- Remarque sur `requirements.txt` vs `environment.yml`:
  - `pip freeze` peut contenir des entrées du type `package @ file://...` lorsque
    les paquets ont été installés via des wheels conda locaux. Ces lignes ne se
    convertissent pas proprement en `package==version` pour `pip install`.
  - Si vous utilisez conda localement, préférez partager un `environment.yml` pour
    garantir la reproduction exacte de l'environnement.

## Commandes pour enrichir / régénérer `requirements.txt`

Pour mettre à jour `requirements.txt` depuis l'environnement courant (pip):

```bash
# régénère et filtre les entrées locales conda (file://)
pip freeze | grep -v "@ file://" > requirements.txt

# (optionnel) ouvrir et nettoyer manuellement les entrées restantes
# puis commit
git add requirements.txt
git commit -m "Update requirements.txt (trimmed to runtime deps)"
git push origin dev_serge
```

Si l'environnement est conda et que vous voulez un export complet :

```bash
conda env export --no-builds > environment.yml
git add environment.yml
git commit -m "Add environment.yml (conda environment export)"
git push origin dev_serge
```
